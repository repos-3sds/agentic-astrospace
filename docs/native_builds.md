# Native Builds (Capacitor)

Covers Epic M11-US01. The Angular application is packaged for iOS and Android
with Capacitor; there is no second codebase and no product logic in the native
projects.

## What is committed

`ui/android` and `ui/ios` are committed because they hold real configuration —
bundle identifier, permissions, icons, entitlements — that must be reviewable.
Their build output and the synced web bundle are not committed:
`npx cap sync` regenerates those from `frontend/dist` on every build, so
tracking them produces nothing but merge conflicts.

## Commands

```bash
cd ui

npm run build:native      # ng build --configuration production && npx cap sync
npm run open:ios          # opens Xcode
npm run open:android      # opens Android Studio
```

Use `build:native` rather than `npx cap sync` on its own. `sync` copies
whatever already sits in `frontend/dist`, so running it after editing source
but before rebuilding ships a stale bundle into the app — with no error.

## API origin

This is the one difference between web and native, and it fails silently if
missed.

On the web, FastAPI serves the SPA, so the API shares the page's origin and a
relative path (`/api/v1/...`) is correct — it follows the deployment to
whatever host it lands on.

A Capacitor WebView serves the bundle from `https://localhost`. A relative path
there resolves against the *bundle*, not the server, so every request 404s
inside the app with nothing in the network log to explain it.

`ui/src/app/core/api-origin.ts` resolves this:

| Platform | Origin |
| --- | --- |
| Web (`ng serve`, deployed SPA) | relative, unchanged |
| Native | `environment.nativeApiOrigin`, absolute |

Set `nativeApiOrigin` in `ui/src/environments/environment.prod.ts` before
building for a device. It is deliberately empty by default: an empty value
throws immediately with an explanatory message, whereas a wrong one surfaces
later as an opaque CORS failure.

A simulator can reach the host on `http://localhost:8000`. A physical device
cannot, and needs the machine's LAN address or the deployed URL.

## CORS

Because the WebView is a genuine cross-origin caller, the API must allow its
origin. `main.py` includes `https://localhost` and `capacitor://localhost` in
the defaults. Any deployment that overrides `ALLOWED_ORIGINS` must keep them,
or the native apps will fail on device only.

## Host requirements

Building for a simulator needs Xcode's iOS **platform** component, which is a
separate download from the SDK stubs. Without it every destination resolves to
the "Any iOS Device" placeholder and xcodebuild reports:

```text
IDERunDestination: Supported platforms for the buildables in the current scheme is empty.
error: iOS 26.5 is not installed. Please download and install the platform from
       Xcode > Settings > Components.
```

Install it from **Xcode > Settings > Components**, or:

```bash
xcodebuild -downloadPlatform iOS
```

`xcodebuild -showsdks` listing an iOS SDK is not sufficient — the SDK stub and
the platform component are tracked separately, so the SDK can appear installed
while the platform is missing.

Android likewise needs the Android SDK; `npx cap add android` warns
`Unable to infer default Android SDK settings` when it is absent.

## Release builds and store submission

**Android.** `ui/android/app/build.gradle` signs the `release` build type from
`ui/android/keystore.properties` (gitignored; copy
`keystore.properties.example`). Without the file the release build is left
unsigned, on purpose. Release builds are minified and resource-shrunk;
`proguard-rules.pro` keeps the Capacitor plugin surface, so a new community
plugin that breaks only in release is almost always a missing keep rule there.

**iOS.** `CapApp-SPM/Package.swift` is regenerated by `npx cap update` and is
committed; run that after adding or removing a plugin, or the iOS build will
link yesterday's plugin list (the Network plugin was missing this way for
weeks). Xcode writes `Package.resolved` on first resolve; commit it once it
exists. `Info.plist` declares `ITSAppUsesNonExemptEncryption = false`: the app
uses only HTTPS and standard algorithms (SQLCipher for the on-device cache),
which fall under the mass-market exemption — confirm that reading against
the current export rules before the first upload. `PrivacyInfo.xcprivacy`
declares UserDefaults (CA92.1) for `@capacitor/preferences`; any new plugin
that touches a required-reason API needs its own entry (file timestamps, C617.1, are
declared for `@capacitor/filesystem`, which stages the shared Ask PDF in the
app cache).

**Voice input.** Ask-by-voice uses `@capacitor-community/speech-recognition`
(`ui/src/app/core/speech.service.ts`). Android links it through Gradle and
asks for `RECORD_AUDIO` at first use. The plugin ships no `Package.swift`, so
the SPM-only iOS project does not link it: there `available()` rejects, the
service reports no support and the composer hides its microphone. Browsers
with the Web Speech API (Chrome, Safari) get voice without any plugin. When
the plugin gains SPM support, `npx cap update` picks it up and iOS needs only
the `NSMicrophoneUsageDescription` and `NSSpeechRecognitionUsageDescription`
strings already in `Info.plist`.

**Sign in with Apple.** App Review guideline 4.8 requires it because Google
sign-in is offered. It runs through Supabase's hosted flow in the system
browser, like Google, so the app needs no entitlement for it. The button shows
only on iOS and only once the Supabase project's Apple provider is on
(`AuthService.appleSignInEnabled()` reads `/auth/v1/settings`). The provider's
secret is a JWT signed with an Apple key and expires after six months, so it
must be regenerated in Supabase before then or Apple sign-in stops working.

**iPhone only.** `TARGETED_DEVICE_FAMILY` is 1. iPads still run the app in
iPhone mode, and the store listing needs no iPad screenshots or iPad review.

**Both.** The Supabase session lives in Keychain / Keystore-backed storage
(`ui/src/app/core/session-storage.ts`), never in Preferences. Terms and the
privacy policy are served by the API at `/legal/terms` and `/legal/privacy`;
the store listings point at the deployed URLs.

## Startup, splash, keyboard and insets

- **Splash.** `launchAutoHide` is false. `App` hides the native splash once
  the animated web intro has painted (`afterNextRender`), and again when boot
  settles as a safety net. If that call is ever removed the app sits on the
  splash forever.
- **Boot does not wait on the network** beyond one bounded step: auth config
  comes from the device and is revalidated behind, the session refresh gives
  up after 8 s, `/settings` syncs in the background, and the profile list is
  cache-first. API GETs time out at 8 s and retry once.
- **The native root carries no PrimeNG.** The web app's chrome lives in
  `shell/web-shell`, loaded lazily for routes outside `/m`. Do not import
  PrimeNG, the sidebar or the kundli dialog into `app.ts` or anything under
  `features/mobile`; the initial budget in `angular.json` fails the build at
  1.2 MB.
- **Keyboard.** `@capacitor/keyboard` resizes the WebView on iOS
  (`resize: 'native'`) and the accessory bar is hidden at runtime; Android 15+
  is resized by Capacitor 8's SystemBars. While the keyboard is up the body
  carries `as-keyboard-open` and the tab bar is hidden.
- **Insets.** `--as-safe-*` read `env(safe-area-inset-*)` and SystemBars'
  injected `--safe-area-inset-*`; there is no hard-coded Android bottom any
  more. Re-check on device after changing either.

## App icon

The app icon is the Nine-Arm Galaxy drawn as gold light ribbons on space
black, with eight small flare-star grahas and a bright core, rendered from one
canvas drawing in `ui/scripts/brand/luminous.cjs`. It is the same icon in every
theme: it does not follow the device or the in-app Light/Dark setting.

- **iOS.** The `AppIcon` set's light and dark appearances are the same image;
  the tinted appearance is a white silhouette for when the user turns on
  tinted icons in iOS 18.
- **Android.** One launcher icon; the adaptive icon carries a monochrome layer
  for Android 13+ themed icons, which the user opts into.
- PWA icons and the favicon use the same drawing.

After changing the drawing, regenerate from `ui/`:

```sh
node scripts/brand/render-icons.cjs && python3 scripts/brand/finish_icons.py
```

The splash screen and the onboarding logo are separate and use the
sun-and-orbits mark in `ui/src/app/shell/splash/splash.component.ts`.

## Push notifications

Registration lives in `ui/src/app/core/push.service.ts` and is opt-in from
Settings › Notifications; the worker that sends is
`python -m astrospace.notifications.worker` (see `astrospace/notifications/`).
A build delivers nothing until these are in place, none of them committed:

- **Android:** `ui/android/app/google-services.json` from the Firebase
  console, downloaded for the Android app registered as
  `app.asksiddha.mobile`. A file for any other package name fails the
  build with "No matching client found for package name". `build.gradle` already applies the google-services plugin only
  when the file exists, so a build without it still runs; it just gets no
  token. `POST_NOTIFICATIONS` is declared in the manifest and requested at
  runtime by the plugin.
- **iOS:** the Push Notifications capability on the App ID and in the
  provisioning profile. `ui/ios/App/App/App.entitlements` carries
  `aps-environment` (development; Xcode switches it to production for an
  archive) and `AppDelegate.swift` forwards the APNs token to the plugin.
  The worker sends to Apple directly (`ApnsTransport` in
  `astrospace/notifications/push.py`); there is no Firebase SDK and no
  `GoogleService-Info.plist` in the iOS app. It needs an APNs auth key
  (.p8, Apple Developer > Keys) mounted into the worker as
  `APNS_KEY_FILE`, with `APNS_KEY_ID` and `APNS_TEAM_ID`. A token is tried
  on production APNs first (TestFlight, App Store) and then on sandbox
  (a build run from Xcode).
- **Server:** `FCM_SERVICE_ACCOUNT_FILE` (and optionally `FCM_PROJECT_ID`)
  in the worker's environment, pointing at a Firebase service-account JSON
  with the Cloud Messaging role. Without it every send fails with
  "fcm transport not configured" and the job stays pending, so configuring
  it later drains the backlog. Run the worker once a day or on a loop; it
  is idempotent per user per day.

## Verified on iOS

The development bundle has been built, synced, installed, and launched on
iPhone 17 Pro simulators running iOS 26.2 and 26.5. The edge-to-edge WebView,
status/home safe areas, unauthenticated landing bootstrap, and restored-session
handoff into `/m` are verified.

Local real-auth configuration is enabled and its API accepts the native
`https://localhost` origin. Cloud Run revision
`agentic-astrospace-00024-5rf` was deployed with that configuration and serves
100% of traffic; the production native preflight now returns HTTP 200.

The iOS and Android projects register
`app.asksiddha.mobile://auth/callback`. OAuth launches in the system browser,
PKCE callbacks are exchanged for a Supabase session, magic-link token
callbacks are accepted, and password recovery lands on `/m/reset-password`.
Supabase must allowlist the callback URL before those hosted flows can return
to the app.

The production Android bundle has also been built, installed, and launched on
the API 36.1 `Medium_Phone` emulator. Landing rendering, keyboard resize, route
Back, and callback-intent delivery are verified. Build Android with Android
Studio's bundled JDK 21; the host's Java 25 is newer than this Gradle/Groovy
toolchain supports.

No controlled test inbox or test credentials are configured in the workspace,
so email confirmation and password-reset delivery have not been exercised
against a real account. Do not create disposable Supabase users without one.
