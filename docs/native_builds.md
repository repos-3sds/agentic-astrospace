# Native Builds (Capacitor)

Covers Epic M11-US01. The Angular application is packaged for iOS and Android
with Capacitor; there is no second codebase and no product logic in the native
projects.

## What is committed

`ui/android` and `ui/ios` are committed because they hold real configuration —
bundle identifier, permissions, icons, entitlements — that must be reviewable.
Their build output and the synced web bundle are not committed:
`npx cap sync` regenerates those from `frontend/dist` on every build, so
tracking them produces nothing but merge conflicts.

## Commands

```bash
cd ui

npm run build:native      # ng build --configuration production && npx cap sync
npm run open:ios          # opens Xcode
npm run open:android      # opens Android Studio
```

Use `build:native` rather than `npx cap sync` on its own. `sync` copies
whatever already sits in `frontend/dist`, so running it after editing source
but before rebuilding ships a stale bundle into the app — with no error.

## API origin

This is the one difference between web and native, and it fails silently if
missed.

On the web, FastAPI serves the SPA, so the API shares the page's origin and a
relative path (`/api/v1/...`) is correct — it follows the deployment to
whatever host it lands on.

A Capacitor WebView serves the bundle from `https://localhost`. A relative path
there resolves against the *bundle*, not the server, so every request 404s
inside the app with nothing in the network log to explain it.

`ui/src/app/core/api-origin.ts` resolves this:

| Platform | Origin |
| --- | --- |
| Web (`ng serve`, deployed SPA) | relative, unchanged |
| Native | `environment.nativeApiOrigin`, absolute |

Set `nativeApiOrigin` in `ui/src/environments/environment.prod.ts` before
building for a device. It is deliberately empty by default: an empty value
throws immediately with an explanatory message, whereas a wrong one surfaces
later as an opaque CORS failure.

A simulator can reach the host on `http://localhost:8000`. A physical device
cannot, and needs the machine's LAN address or the deployed URL.

## CORS

Because the WebView is a genuine cross-origin caller, the API must allow its
origin. `main.py` includes `https://localhost` and `capacitor://localhost` in
the defaults. Any deployment that overrides `ALLOWED_ORIGINS` must keep them,
or the native apps will fail on device only.

## Host requirements

Building for a simulator needs Xcode's iOS **platform** component, which is a
separate download from the SDK stubs. Without it every destination resolves to
the "Any iOS Device" placeholder and xcodebuild reports:

```text
IDERunDestination: Supported platforms for the buildables in the current scheme is empty.
error: iOS 26.5 is not installed. Please download and install the platform from
       Xcode > Settings > Components.
```

Install it from **Xcode > Settings > Components**, or:

```bash
xcodebuild -downloadPlatform iOS
```

`xcodebuild -showsdks` listing an iOS SDK is not sufficient — the SDK stub and
the platform component are tracked separately, so the SDK can appear installed
while the platform is missing.

Android likewise needs the Android SDK; `npx cap add android` warns
`Unable to infer default Android SDK settings` when it is absent.

## Release builds and store submission

**Android.** `ui/android/app/build.gradle` signs the `release` build type from
`ui/android/keystore.properties` (gitignored; copy
`keystore.properties.example`). Without the file the release build is left
unsigned, on purpose. Release builds are minified and resource-shrunk;
`proguard-rules.pro` keeps the Capacitor plugin surface, so a new community
plugin that breaks only in release is almost always a missing keep rule there.

**iOS.** `CapApp-SPM/Package.swift` is regenerated by `npx cap update` and is
committed; run that after adding or removing a plugin, or the iOS build will
link yesterday's plugin list (the Network plugin was missing this way for
weeks). Xcode writes `Package.resolved` on first resolve; commit it once it
exists. `Info.plist` declares `ITSAppUsesNonExemptEncryption = false`: the app
uses only HTTPS and standard algorithms (SQLCipher for the on-device cache),
which fall under the mass-market exemption — confirm that reading against
the current export rules before the first upload. `PrivacyInfo.xcprivacy`
declares UserDefaults (CA92.1) for `@capacitor/preferences`; any new plugin
that touches a required-reason API needs its own entry (file timestamps, C617.1, are
declared for `@capacitor/filesystem`, which stages the shared Ask PDF in the
app cache).

**Voice input.** Ask-by-voice uses `@capacitor-community/speech-recognition`
(`ui/src/app/core/speech.service.ts`). Android links it through Gradle and
asks for `RECORD_AUDIO` at first use. The plugin ships no `Package.swift`, so
the SPM-only iOS project does not link it: there `available()` rejects, the
service reports no support and the composer hides its microphone. Browsers
with the Web Speech API (Chrome, Safari) get voice without any plugin. When
the plugin gains SPM support, `npx cap update` picks it up and iOS needs only
the `NSMicrophoneUsageDescription` and `NSSpeechRecognitionUsageDescription`
strings already in `Info.plist`.

**Sign in with Apple.** App Review guideline 4.8 requires it because Google
sign-in is offered. It runs through Supabase's hosted flow in the system
browser, like Google, so the app needs no entitlement for it. The button shows
only on iOS and only once the Supabase project's Apple provider is on
(`AuthService.appleSignInEnabled()` reads `/auth/v1/settings`). The provider's
secret is a JWT signed with an Apple key and expires after six months, so it
must be regenerated in Supabase before then or Apple sign-in stops working.

**iPhone only.** `TARGETED_DEVICE_FAMILY` is 1. iPads still run the app in
iPhone mode, and the store listing needs no iPad screenshots or iPad review.

**Play release checklist.** Before any AAB goes to a Play track (owner: Hawk,
in Play Console):

1. *App content > Foreground service permissions*: declare **Media playback**
   for `BriefSpeechService` (the Listen widget reads today's brief aloud with
   a Stop notification). Play wants a short screen recording: add the Listen
   widget, tap it, show the notification with Stop, tap Stop. Without the
   declaration the upload is rejected because of
   `FOREGROUND_SERVICE_MEDIA_PLAYBACK` in the manifest.
2. *Data safety*: unchanged unless a new SDK was added since the last upload.
3. Build the signed AAB on the Mac (`versionCode` is the commit count, set by
   `npm run version:sync`), upload it to internal testing with
   `scripts/play_upload.py` (below), and test the build on the phone before it
   goes to closed testing.
4. *Release notes* for the first build after #161: "Mantra counts now start
   fresh each day, on your phone's date. A day finished just before the
   update may show once more, or not at all." Old `completedDates` were UTC
   dates, and the tracker now uses the local date (D22). This is intended,
   so the dates are not rewritten.

**Uploading to Play.** `scripts/play_upload.py` sends a signed AAB to a
testing track and rolls it out (status `completed`), so nobody drags files into
Play Console. It needs only Python 3 and `openssl`, both already on the Mac:
nothing to install. It authenticates as the service account
`play-publisher@gen-lang-client-0058562386.iam.gserviceaccount.com`, whose
Play Console access is this app only, "Release apps to testing tracks" plus
read-only, with no production or financial rights. The key lives outside the
repo at `~/.config/astrospace/play-publisher.json` (chmod 600; override with
`PLAY_SERVICE_ACCOUNT_JSON`). Never print it, copy it into the repo, or paste
it into a thread; `.gitignore` also blocks `*service-account*.json`.

The script accepts only `internal` (default) and `alpha` (closed testing) and
refuses `production` before making any request. It does everything inside one
Play edit and deletes the edit if any step fails, so a failed run leaves Play
unchanged. It refuses a `versionCode` that is not above what the track already
holds; since `versionCode` counts commits, that means building from a newer
commit, never hand-editing the number.

"Build AAB from latest main" on the Mac, end to end:

```bash
cd ~/Documents/agentic-astrospace
git checkout main && git pull --ff-only origin main
cd ui && npm ci && npm run build:native
cd android
JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home" ./gradlew bundleRelease
cd ../..
AAB=ui/android/app/build/outputs/bundle/release/app-release.aab
VC=$(git rev-list --count HEAD)
cp "$AAB" ~/Documents/AskSiddha-builds/asksiddha-$VC.aab
python3 scripts/play_upload.py "$AAB" --notes "What changed, in one or two plain lines."
```

Everything above the last line is the existing build; if the Mac has a
working variant of it (a different JDK path, `npm install` instead of `npm ci`),
keep that. The last line is the new step, and it prints
`Done: versionCode N is live on the internal track`.
Internal testers get the update from the Play Store app within minutes. To put
the same build on closed testing, release the bundle Play already holds:
`python3 scripts/play_upload.py --version-code N --track alpha --notes "…"`.
Uploading the .aab again fails, because Play refuses a versionCode it has
already received. Google reviews closed-testing releases before testers see
them.

`python3 scripts/play_upload.py --check` verifies the key and access and shows
what each track holds, without changing anything; run it first after rotating
the key. Release notes are optional, go out in `en-IN` (the listing's default
language) and are capped at 500 characters. If a commit fails with "Changes
cannot be sent for review automatically", rerun with
`--changes-not-sent-for-review` and send the changes for review in Play
Console. Uploading does not replace the checklist above: the foreground
service declaration and Data safety are still answered in Play Console.

**Both.** The Supabase session lives in Keychain / Keystore-backed storage
(`ui/src/app/core/session-storage.ts`), never in Preferences. Terms and the
privacy policy are served by the API at `/legal/terms` and `/legal/privacy`;
the store listings point at the deployed URLs.

## Startup, splash, keyboard and insets

- **Splash.** `launchAutoHide` is false. `App` hides the native splash once
  the animated web intro has painted (`afterNextRender`), and again when boot
  settles as a safety net. If that call is ever removed the app sits on the
  splash forever.
- **Boot does not wait on the network** beyond one bounded step: auth config
  comes from the device and is revalidated behind, the session refresh gives
  up after 8 s, `/settings` syncs in the background, and the profile list is
  cache-first. API GETs time out at 8 s and retry once.
- **The native root carries no PrimeNG.** The web app's chrome lives in
  `shell/web-shell`, loaded lazily for routes outside `/m`. Do not import
  PrimeNG, the sidebar or the kundli dialog into `app.ts` or anything under
  `features/mobile`; the initial budget in `angular.json` fails the build at
  1.2 MB.
- **Keyboard.** `@capacitor/keyboard` resizes the WebView on iOS
  (`resize: 'native'`) and the accessory bar is hidden at runtime; Android 15+
  is resized by Capacitor 8's SystemBars. While the keyboard is up the body
  carries `as-keyboard-open` and the tab bar is hidden.
- **Insets.** `--as-safe-*` read `env(safe-area-inset-*)` and SystemBars'
  injected `--safe-area-inset-*`; there is no hard-coded Android bottom any
  more. Re-check on device after changing either.

## Native Google sign-in

Google's consent screen and its "You shared some Google Account data with ..."
email name the host the OAuth redirect runs through, which for Supabase's
hosted flow is `wcaqjhqckipgkvhbiwjt.supabase.co`. On a phone the app now uses
Google's own sign-in sheet instead (`@capgo/capacitor-social-login`:
Credential Manager on Android, the Google Sign-In SDK on iOS) and hands the ID
token to Supabase with `signInWithIdToken`, so no Supabase page opens.
`AuthService.signInWithGoogle` falls back to the hosted browser flow on any
failure other than a cancel, and whenever the server sends no client IDs, so a
half-finished setup behaves exactly like before. Web sign-in is unchanged.

The nonce: the app sends `sha256(raw)` to Google, which signs it into the ID
token, and gives Supabase the raw value, which checks one against the other.
Leave Supabase's "Skip nonce checks" off.

Setup, all in Google Cloud project `gen-lang-client-0058562386` (the one that
owns the Web client Supabase's Google provider uses):

1. **Android OAuth clients** (Google Auth Platform → Clients → Create →
   Android), package `app.asksiddha.mobile`, one per signing certificate:
   - the **Play app signing key** SHA-1 (Play Console → Test and release →
     App integrity → App signing key certificate). Every Play-installed build
     is signed with this one.
   - the **upload key** SHA-1 (`keytool -list -v -keystore
     ui/android/upload-key.jks`), for AABs/APKs installed by hand.
   - optionally the debug key (`cd ui/android && ./gradlew signingReport`).
   The Android client IDs are not used anywhere in code.
2. **API env**: `GOOGLE_OAUTH_WEB_CLIENT_ID=<the Web client ID>` on the Cloud
   Run service (it is public; it already ships in every Google sign-in URL).
   The app reads it from `/api/v1/auth/config`, caches it, and uses it from
   the next launch after it first sees it.
3. **iOS** (when building for iPhone): create an iOS OAuth client with bundle
   ID `app.asksiddha.mobile`; add its reversed ID
   (`com.googleusercontent.apps.<...>`) to `ui/ios/App/App/Info.plist`
   under `CFBundleURLTypes` → `CFBundleURLSchemes`; add the iOS client ID to
   Supabase → Authentication → Providers → Google → "Client IDs" after the
   Web one (comma-separated), then set `GOOGLE_OAUTH_IOS_CLIENT_ID`. Until
   then iOS keeps the browser flow.

`capacitor.config.ts` bundles the Google provider only; Facebook is off, which
also keeps the `AD_ID` permission out of the Android build. On Android a
`[28444] Developer console is not set up correctly` in Logcat (tag
`GoogleProvider`) means the SHA-1 of the installed build is not on an Android
client; the app quietly uses the browser meanwhile.

## Home-screen widgets

Android has eight widgets, all drawn natively from data the app publishes;
none of them call the server. Code: `ui/android/.../widgets/` and
`ui/src/app/core/widget-bridge.service.ts`.

| Widget | Shows | Tap |
| --- | --- | --- |
| Your day | score ring with the day's word (Steady, Mixed, Take care) under the number; medium adds the date, headline and a timing chip; large adds the tithi, summary, and one Do and one Avoid as tinted glass cards | Today |
| Listen | 2x2 by default: a big play/stop button, the day's word and the brief's length; 4x2 adds the day's headline; squashed to one row, a slim bar | play/stop |
| Calendar | the next 7 days, tinted good day / take care as the Calendar tab, with a dot for a festival or vrat and the week's festivals listed (one row at 4x2, more when taller); at 2x2, today alone with its tithi and day quality. No month view (Hawk, 2026-10-21) | Calendar |
| Timing | the next window (Rahu Kalam first): "Starts in 1h 16m", its times, and a ring that fills over the 3 hours before it and empties while it runs | Calendar |
| Moon | tonight's phase, the tithi, and the next Purnima or Amavasya by date | Calendar |
| Mantra | the practice last opened, today's count; tap the ring to count | the practice |
| Ask | a search bar into Ask | Ask |
| Today's Subhashita | the app's Subhashita card (same red-to-dark ground in both themes): the first Sanskrit line, the plain meaning in gold and the source; 4x3 and up, the whole card with wordmark, full verse, English and meaning | the verse screen, to share |

How it fits together:

- The app publishes JSON "parts" (`today`, `calendar`, `subhashita`,
  `mantra`) through the `SiddhaWidgets` plugin into SharedPreferences.
  Today publishes only the account holder's own day, not whichever profile
  is open. Sign-out clears every part.
- A part is only shown for its own date, so a phone that hasn't opened the
  app today shows "Open Siddha" rather than yesterday's reading. Verses go
  out 14 days ahead, so the verse widget works offline for two weeks.
- Widgets refresh at the next window boundary or midnight (inexact alarm,
  no exact-alarm permission), every 30 minutes, and after reboot, time or
  timezone changes. While a window is ahead or running, a per-minute
  non-wakeup alarm redraws only Timing and Your day, so countdowns read in
  minutes and never show seconds.
- Look: the app's two themes, Cream Glass by day and Liquid Glass by night
  (`values/` and `values-night/widget_colors.xml`; the card is
  `drawable/widget_card.xml`, a ground plus the theme's radial glows and a
  hairline edge), in the app's own Inter and Playfair (`res/font/`, static
  cuts of `ui/public/fonts/`) so launchers don't substitute the phone's
  font. The Subhashita wordmark is Samarkan cut down to the letters of
  "Siddha" (`res/font/samarkan_wordmark.ttf`). Font resources need Android
  8+; older phones fall back to the system face.
- Layouts: only views RemoteViews can inflate (`FrameLayout`, `LinearLayout`,
  `TextView`, `ImageView` and the other @RemoteView classes). A plain
  `<View>` or `<Space>` builds and passes aapt, then the launcher says
  "Couldn't add widget"; that broke Calendar, Subhashita and the large Your
  day in #230. Use an empty `FrameLayout`. `tests/test_android_widgets.py`
  checks every widget layout.
- Opacity: each widget's card is an `ImageView` (`widget_bg`) under the
  content, faded by `Widgets.applyOpacity` to the reader's setting
  (Settings > Light or dark > Home screen widgets, 0-100%, Android only).
  It is stored in its own prefs file (`siddha_widget_look`), so signing out
  keeps it; the text is never faded.
- Text size: widget text follows the phone's font size only between 100%
  and 115% (`Widgets.MIN_TEXT_SCALE`, `MainActivity.MAX_TEXT_ZOOM`); outside
  that it is drawn at the nearer limit. The smallest widget text is 10sp.
- The calendar part also carries `days` (each of the next 7 days' tithi and
  the reader's good / mixed / care quality from `/panchanga/{id}/month`, as
  the Calendar tab) and `vrats` (`/festivals/vrat-days`), both fetched by
  `publishCalendar`; a day without them draws plain.
- Mantra taps on the widget are held natively and folded into the tracker's
  record when the app next opens, so both show one count. The count is per
  local day.
- Listen plays Siddha's natural voice (the Listen sheet's Chirp audio) when
  the reader's plan has it and they haven't picked a phone voice: Today
  hands the widget one MP3 per piece (`publishListenAudio`, from the
  device or server cache, which the worker pre-renders), stored in
  `files/listen-audio/` with the date and text it was made for. Otherwise,
  or if that audio is stale or won't play, it reads with the phone's own
  voice (Android TextToSpeech, en-IN, 0.9x). Either way it runs in a
  `mediaPlayback` foreground service with a Stop notification and reads
  the same script as the Listen sheet. The play button sends one toggle
  and the service decides: a resize or a killed process can leave the
  widget showing the wrong state, and a separate play and stop let a tap
  on the wrong picture do nothing. **Play Console:** App
  content > Foreground service permissions needs a declaration for
  media playback ("reads the daily brief aloud when the user taps play on
  the widget") before an AAB with the widgets can be published.
- Moon days come from `GET /api/v1/festivals/moon-days` (tithi at sunrise,
  shipped with its `observance_note`).

iPhone widgets are deferred until the Apple developer account is active;
see the deferred backlog in
[backend_astro_depth_checklist_2026-08-06.md](backend_astro_depth_checklist_2026-08-06.md).

## App icon

The app icon is the Nine-Arm Galaxy drawn as gold light ribbons on space
black, with eight small flare-star grahas and a bright core, rendered from one
canvas drawing in `ui/scripts/brand/luminous.cjs`. It is the same icon in every
theme: it does not follow the device or the in-app Light/Dark setting.

- **iOS.** The `AppIcon` set's light and dark appearances are the same image;
  the tinted appearance is a white silhouette for when the user turns on
  tinted icons in iOS 18.
- **Android.** One launcher icon; the adaptive icon carries a monochrome layer
  for Android 13+ themed icons, which the user opts into.
- PWA icons and the favicon use the same drawing.

After changing the drawing, regenerate from `ui/`:

```sh
node scripts/brand/render-icons.cjs && python3 scripts/brand/finish_icons.py
```

The splash screen and the onboarding logo are separate and use the
sun-and-orbits mark in `ui/src/app/shell/splash/splash.component.ts`.

## Push notifications

Registration lives in `ui/src/app/core/push.service.ts` and is opt-in from
Settings › Notifications; the worker that sends is
`python -m astrospace.notifications.worker` (see `astrospace/notifications/`).
A build delivers nothing until these are in place, none of them committed:

- **Android:** `ui/android/app/google-services.json` from the Firebase
  console, downloaded for the Android app registered as
  `app.asksiddha.mobile`. A file for any other package name fails the
  build with "No matching client found for package name". `build.gradle` already applies the google-services plugin only
  when the file exists, so a build without it still runs; it just gets no
  token. `POST_NOTIFICATIONS` is declared in the manifest and requested at
  runtime by the plugin.
- **iOS:** the Push Notifications capability on the App ID and in the
  provisioning profile. `ui/ios/App/App/App.entitlements` carries
  `aps-environment` (development; Xcode switches it to production for an
  archive) and `AppDelegate.swift` forwards the APNs token to the plugin.
  The worker sends to Apple directly (`ApnsTransport` in
  `astrospace/notifications/push.py`); there is no Firebase SDK and no
  `GoogleService-Info.plist` in the iOS app. It needs an APNs auth key
  (.p8, Apple Developer > Keys) mounted into the worker as
  `APNS_KEY_FILE`, with `APNS_KEY_ID` and `APNS_TEAM_ID`. A token is tried
  on production APNs first (TestFlight, App Store) and then on sandbox
  (a build run from Xcode).
- **Server:** `FCM_SERVICE_ACCOUNT_FILE` (and optionally `FCM_PROJECT_ID`)
  in the worker's environment, pointing at a Firebase service-account JSON
  with the Cloud Messaging role. Without it every send fails with
  "fcm transport not configured" and the job stays pending, so configuring
  it later drains the backlog. Run the worker once a day or on a loop; it
  is idempotent per user per day.

## Verified on iOS

The development bundle has been built, synced, installed, and launched on
iPhone 17 Pro simulators running iOS 26.2 and 26.5. The edge-to-edge WebView,
status/home safe areas, unauthenticated landing bootstrap, and restored-session
handoff into `/m` are verified.

Local real-auth configuration is enabled and its API accepts the native
`https://localhost` origin. Cloud Run revision
`agentic-astrospace-00024-5rf` was deployed with that configuration and serves
100% of traffic; the production native preflight now returns HTTP 200.

The iOS and Android projects register
`app.asksiddha.mobile://auth/callback`. OAuth launches in the system browser,
PKCE callbacks are exchanged for a Supabase session, magic-link token
callbacks are accepted, and password recovery lands on `/m/reset-password`.
Supabase must allowlist the callback URL before those hosted flows can return
to the app.

The production Android bundle has also been built, installed, and launched on
the API 36.1 `Medium_Phone` emulator. Landing rendering, keyboard resize, route
Back, and callback-intent delivery are verified. Build Android with Android
Studio's bundled JDK 21; the host's Java 25 is newer than this Gradle/Groovy
toolchain supports.

No controlled test inbox or test credentials are configured in the workspace,
so email confirmation and password-reset delivery have not been exercised
against a real account. Do not create disposable Supabase users without one.
